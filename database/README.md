# ბაზის სკრიპტები

## გაშვების თანმიმდევრობა

1. `00_create_database.sql`
2. `auth/01_users_table.sql` → `auth/02_users_procedures.sql` → `auth/03_seed_users.sql` *(მხოლოდ ლოკალურად)*
3. `sp122/01_table.sql` → `sp122/02_procedures.sql` → `sp122/04_import_real_data.sql` *(რეალური მონაცემები, 3267 ჩანაწერი)*
   ან, რეალური მონაცემების ნაცვლად, `sp122/03_seed_data.sql` *(3 სატესტო ჩანაწერი)*

ყველა სკრიპტი შეიძლება რამდენჯერმე გაეშვას: ცხრილები `IF ... IS NULL`-ით იქმნება,
procedure-ები `CREATE OR ALTER`-ით.

## ახალი ცნობარის დამატება

საქაღალდე `database/<ცნობარი>/`:

| ფაილი | შიგთავსი |
|---|---|
| `01_table.sql` | ცხრილი |
| `02_procedures.sql` | `<X>_GetList`, `<X>_GetById`, `<X>_Insert`, `<X>_Update`, `<X>_Delete` |
| `03_seed_data.sql` | სატესტო მონაცემები |

## procedure-ების წესები

- `GetList` იღებს `@Search`, `@Page`, `@PageSize` (`0` = ყველა) და აბრუნებს სვეტს `TotalCount`.
- `Insert` და `Update` აბრუნებენ შენახულ ჩანაწერს.
- შეცდომა — `THROW` ქართული შეტყობინებით:

| კოდი | HTTP | მნიშვნელობა |
|---|---|---|
| 50001 | 400 | არასწორი მონაცემი |
| 50002 | 409 | კონფლიქტი (დუბლიკატი, გადაფარვა) |
| 50004 | 404 | ჩანაწერი ვერ მოიძებნა |

## SP-122: რეალური მონაცემების განახლება Excel-იდან

1. Excel-ის ფაილი შეინახეთ `.xlsx` ფორმატში
2. `pip install openpyxl` (ერთხელ)
3. `python3 database/sp122/import/convert_sp122.py <ფაილი.xlsx>`
   - აღადგენს დაზიანებულ ხაზებს, გადაიყვანს `naz_gr`-ს ძველი კოდირებიდან (Georgian-PS) ქართულ Unicode-ში,
     შეამოწმებს მონაცემებს და შექმნის `import/sp122_clean.csv`-ს და `04_import_real_data.sql`-ს
4. DataGrip-ში გაუშვით `04_import_real_data.sql` — ცხრილის შიგთავსი მთლიანად ჩანაცვლდება

### SP-122-ის ციფრობრივი წესი

ჩანაწერი ვაგონებს ნომრის **ციფრების** მიხედვით აღწერს: ვაგონი ეკუთვნის ჩანაწერს, თუ მისი პირველი 3 ციფრი,
მე-4, მე-5, მე-6 და მე-7 ციფრი შესაბამისად ng-ისა და vg-ის ციფრებს შორისაა (მე-8 საკონტროლოა).
ეს ლოგიკა გამოიყენება ნომრით ძებნისას; შენახვისას გადაკვეთის პოლიტიკა აღწერილია ქვემოთ.

### SP-122-ის ვალიდაციების განახლება

არსებულ ბაზაზე გაუშვით მხოლოდ `sp122/01_table.sql` და შემდეგ `sp122/02_procedures.sql`.
იმპორტის/seed-ის სკრიპტების ხელახლა გაშვება საჭირო არ არის.

- ქვედა და ზედა ზღვარი რვანიშნაა, მთავრდება შესაბამისად 0-ით და 9-ით; ng < vg.
- kol, ves, udl, dm, rod და utv სავალდებულო არანულოვანი რიცხვებია; დადებითობა დამატებით არ მოითხოვება.
- utv-ის სიგრძე მოწმდება ძველი STR(Value)-ის რიცხვითი ქცევით (წინა ნულების გარეშე, ნულ ათწილადამდე დამრგვალებით).
  39000000–39999999 და 50000000–59999999 ინტერვალებში სიგრძეა 4, სხვაგან — 3.
- რიცხვითი ინტერვალების ნებისმიერი გადაკვეთა მხოლოდ გაფრთხილებაა, საკუთარი ჩანაწერის გამოკლებით.
  `01_table.sql` არსებულ UQ_SP122_Range შეზღუდვას ხსნის; იდენტური დიაპაზონიც მხოლოდ გაფრთხილებაა.
- naz_gr და naz_rus შენახვამდე იჭრება 70 Unicode სიმბოლომდე, კიდეების სივრცეების მოცილებით.
- წინა, ციფრების მიხედვით გადაფარვის აკრძალვა აღარ მოქმედებს. ზემოთ აღწერილი ციფრობრივი წესი მხოლოდ ნომრით ძებნას ეხება.
- ისტორიული ჩანაწერები არ გადაიწერება; დამატება/ცვლილება ახალ წესებს უნდა აკმაყოფილებდეს.
- ველების თანმიმდევრული TabStop/LostFocus ჩაკეტვა არ გადმოტანილა; წესები მოწმდება ფორმაში და შენახვისას API/SQL-შიც.

ვალიდაციების ტესტები:

- კლიენტი: `cd nsi-client && npm test -- --watch=false`
- სერვერის მოდელი (.NET 10 SDK): `dotnet run --project tests/Sp122.ValidationChecks`

### macOS-ზე გაშვება

.NET 10 SDK საჭიროა (`~/.dotnet/dotnet --version`). `launchSettings.json`-ში ჩართულია
`DOTNET_USE_POLLING_FILE_WATCHER=1`, რათა macOS-ის native file watcher-მა API-ის გაშვება არ შეაფერხოს.

კლიენტის npm ბრძანებები Angular CLI-ს `scripts/angular-cli.mjs`-ით უშვებს.
ის იყენებს SQLite build cache-ს LMDB native მოდულის ავარიული დასრულების თავიდან ასაცილებლად.
